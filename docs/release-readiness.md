# قائمة جاهزية الإطلاق الرسمي لتطبيق «دفء»

**الغرض:** تحديد الحد الأدنى العملي قبل إطلاق «دفء» على App Store وGoogle Play، مع التركيز على الخصوصية المحلية وسلامة بيانات الأسرة. هذه القائمة لا تجعل أي ميزة إضافية شرطًا للإطلاق؛ لا يُؤجَّل الإطلاق إلا بسبب فشل في الأمان أو فقدان البيانات أو تعطل مسار أساسي.

## قاعدة قرار الإطلاق

يُعد التطبيق جاهزًا عندما تكون جميع البنود الحرجة في حالة **مكتمل**، ولا توجد أعطال تمنع الاستخدام أو تؤدي إلى فقدان البيانات. يمكن تأجيل التحسينات غير الحرجة مثل الزخارف، الرسوم الإضافية، أو الميزات الجديدة إلى ما بعد إطلاق النسخة الأولى.

| المحور | معيار القبول العملي | الحالة المطلوبة |
|---|---|---|
| الوظائف الأساسية | إنشاء فرد، تعديل بياناته، تسجيل شعور وملاحظة، إضافة مناسبة، تعديل وحذف العناصر، ثم إعادة فتح التطبيق دون فقدان البيانات | لا أعطال حرجة |
| النسخ والاستعادة | إنشاء نسخة مشفّرة، استعادة نسخة صحيحة، رفض ملف تالف أو كلمة مرور خاطئة، وإنشاء نسخة وقائية قبل الاستعادة | نجاح 3 دورات متتالية على iOS وAndroid |
| التنبيهات | جدولة تذكير مناسبة والملخص الأسبوعي، اختبار التعديل والإلغاء وعدم تكرار الإشعار | وصول الإشعار في الحالات المدعومة أو ظهور سبب واضح عند رفض الإذن |
| التقارير | إنشاء PDF وCSV، التحقق من العربية والتواريخ، وفحص الفلاتر والنطاق المخصص والسجل | لا نص مقطوع ولا بيانات فرد غير مختار |
| الخصوصية | عدم إرسال بيانات الأسرة دون قصد، وضوح أذونات الكاميرا والإشعارات، وتطابق بيانات الخصوصية مع السلوك الفعلي | مراجعة يدوية مكتملة |
| الوصول | تسميات واضحة لقارئ الشاشة، تباين مقبول، وأهداف لمس قابلة للاستخدام | اختبار المسارات الأساسية دون الاعتماد على الأيقونة وحدها |
| الاستقرار | تشغيل TypeScript وVitest وlint وبناء الإنتاج دون أخطاء | جميع الفحوصات ناجحة |
| المتاجر | اسم ووصف ولقطات شاشة وأيقونة وبيانات تواصل وسياسة خصوصية وبيانات الخصوصية/السلامة دقيقة | جاهز للمراجعة |

## الاختبار النهائي المختصر

ينفّذ شخص لم يطوّر التطبيق السيناريو التالي على جهاز iOS وجهاز Android، باستخدام بيانات تجريبية غير حساسة:

1. يضيف فردين، ثم يسجل شعورًا وملاحظة لكل فرد.
2. يضيف مناسبة قريبة، يعدّلها، ثم يختبر التذكير والإلغاء.
3. ينشئ نسخة احتياطية مشفّرة، يغلق التطبيق، ثم يتأكد من ظهور تاريخ آخر نسخة.
4. يغيّر بيانات تجريبية ويستعيد النسخة، ثم يتحقق من عودة الحالة السابقة.
5. يجرّب ملفًا تالفًا وكلمة مرور خاطئة، ويتأكد من بقاء البيانات الحالية.
6. ينفّذ استعادة عادية ثم يختبر استعادة النسخة الوقائية.
7. ينشئ تقرير PDF وملف CSV، ويفحص العربية، الفلاتر، التواريخ، وسجل العمليات.
8. يرفض أذونات الكاميرا والإشعارات ثم يعيد تفعيلها من إعدادات النظام، ويتأكد من رسائل مفهومة.

تُسجّل النتيجة في جدول بسيط: **الجهاز، إصدار النظام، الخطوة، النتيجة، ولقطة/وصف الخطأ إن وجد**. لا يُستخدم حساب أو بيانات عائلية حقيقية أثناء الاختبار.

## متطلبات الخصوصية والمتاجر

ينبغي إعداد سياسة خصوصية قصيرة ومطابقة للسلوك الفعلي، توضح أن بيانات الأسرة تُحفظ محليًا وما الذي يحدث عند استخدام الصور أو مشاركة التقارير. Apple تطلب تقديم معلومات الخصوصية في App Store Connect، وتحمّل المطوّر مسؤولية دقتها وتحديثها عند تغير الممارسات [1]. كما تشير إرشادات Apple قبل الإرسال إلى ضرورة اختبار الأعطال، اكتمال بيانات التطبيق، وتوفير وصول كافٍ للمراجعة [2].

على Google Play يجب إكمال نموذج **Data safety** وبيان ممارسات جمع البيانات ومشاركتها وحمايتها، حتى عندما لا يجمع التطبيق بيانات خارج الجهاز، مع توفير رابط سياسة الخصوصية حسب حالة النشر [3]. يجب مراجعة مكتبات الطرف الثالث والأذونات الفعلية قبل تعبئة النموذج، لا الاعتماد على افتراض أن التطبيق المحلي لا يحتاج أي إفصاح.

بالنسبة لتطبيق Expo، يجب اختبار build موقّع على مسار اختبار داخلي أو TestFlight قبل الإنتاج. توضح وثائق Expo أن EAS Submit يرفع ملف Android App Bundle أو iOS archive، وأن TestFlight ليس إصدارًا تلقائيًا للإنتاج؛ يلزم إكمال بيانات المتجر واختيار الإصدار وإرساله للمراجعة [4].

## مؤشرات ما بعد الإطلاق خلال أول أسبوعين

| المؤشر | هدف النسخة الأولى |
|---|---|
| أعطال تمنع فتح التطبيق أو فقدان البيانات | صفر أعطال معروفة |
| نجاح إنشاء واستعادة النسخ | 100% في السيناريوهات المدعومة |
| فشل إشعار قابل للتفسير | كل فشل مرتبط بإذن أو إعداد واضح |
| مهام يومية أساسية تحتاج مساعدة | أقل من حالة واحدة لكل خمسة مستخدمين تجريبيين |
| ملاحظات متكررة عن التعقيد | لا توجد خطوة مربكة متكررة لدى أكثر من مستخدمين اثنين |
| طلبات ميزات جديدة | لا تُضاف مباشرة؛ تُجمع وتُرتب بعد ملاحظة الاستخدام الفعلي |

## قرار ما بعد الاختبار

إذا فشل النسخ أو الاستعادة أو ظهرت مشكلة فقدان بيانات، يتوقف الإطلاق حتى الإصلاح وإعادة الاختبار. إذا كان الخلل في تنسيق ثانوي أو نص غير واضح ولا يمنع الاستخدام، يُسجّل للإصدار التالي. لا يُستحسن إضافة ميزة جديدة قبل مرور أسبوع من الاستخدام الفعلي وظهور حاجة متكررة قابلة للقياس.
